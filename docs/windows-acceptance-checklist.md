# AG Relay 真实 Windows 成品验收清单（规格 #19）

对应规格 #19 的「接缝二：真实 Windows 成品验收」。本清单把纯 mock 证明不了的六项交互落成可执行步骤，供维护者在**独立 Windows 沙箱或 VM** 内人工执行。按改动选择受影响条目；只有实际完成全部条目时才报告全项成品通过，不要求每次小改重复执行整份清单。定向验证范围见 [核心维护说明](gateway-core-maintenance.md#快速工作流与定向验证)。

## 为什么不在这台宿主机上跑

现用实例正通过本机网关服务日常使用：宿主机的默认端口、HKCU 自启键、`%APPDATA%\ag-relay\` 日志与设置都被真实使用。真实安装/卸载、更新、强停与自启都属于系统级副作用，**不能在承载现用网关的机器上执行**。哪些测试与命令禁止在承载现用实例的机器上运行，见[网关核心维护说明](gateway-core-maintenance.md)的「现有契约基线与安全运行」。

因此本仓库的取舍是：

- **宿主机只读验签**：`npm run smoke -- -Artifacts <发布物目录>`（`scripts/smoke.ps1`）只读检查 `latest.json` 与两种安装器签名，**不启动应用、不安装、不访问/停止网关**。它证明不了安装成功、实时刷新、更新事务与干净机器运行。
- **VM 内人工验收**：上面宿主机的只读检查**不能**替代本清单；本清单必须在独立沙箱/VM 内完成，才算真实成品通过。报告须区分「只读验签通过」「契约测试通过」与「真实成品通过」。

## 前置准备

1. **独立环境**：全新 Windows Sandbox 或 VM 快照，具备**独立的 Windows 用户配置文件、HKCU 注册表、`%APPDATA%`、安装目录与端口**。只读挂载或复制发布物进入；不把宿主机现用安装目录挂为可写，不复用宿主的网关进程、上游地址或凭据。
2. **干净机器基线（第 ⑤ 项用）**：确认 PATH 中**没有** `node.exe`（`where node` 无结果），也未安装系统 Node，以验证随包 `node.exe` 足够。
3. **测试签名材料与测试更新源**：不要使用生产私钥，也不要上传 GitHub Release。
   - `node scripts/release.mjs test-build --out <一个尚不存在的新空目录>` 会用**一次性临时测试密钥**生成带测试签名的 NSIS/MSI、各自的 `.sig`、`SHA256SUMS`、`latest.json`，以及记录了测试公钥与测试更新端点的 `tauri.test.json`。私钥在构建结束即销毁。
   - 应用内更新要求**被测应用本身信任同一测试公钥**：用 `test-build` 产出的测试配置（`tauri.test.json`，测试公钥 + 测试端点）安装被测版本。
   - **测试更新源**：把 `latest.json` 与对应安装器放到 VM 内一个受控的本地静态服务/目录，并让应用配置的更新端点指向它（例如本地地址加 hosts 重定向）；不连真实发布端点。
4. **受控上游**：给一个**本地假上游**（不回真实上游、不带真实密钥），用于制造在途请求与验证连接设置生效。

## 证据留存

- 每次验收在 **VM 内**建立独立目录，例如 `C:\ag-relay-acceptance\<日期-run>\`，保存：安装前后截图、诊断页截图、连接设置前后截图、更新流程截图、`%APPDATA%\ag-relay\` 内设置与日志副本、命令输出日志。
- 完成后再把该目录整份**导出到宿主机仓库外**的证据目录（沿用既有 `ag-relay-notes\evidence\` 约定；**不要提交进仓库**）。每份证据标注对应的条目编号、构建提交、版本号与测试密钥指纹（不导出私钥）。

## 六项交互验收

### ① 用安装程序安装成功

- **步骤**：在干净 VM 中分别运行 `test-build` 产出的 NSIS `.exe` 与 MSI `.msi`（各一次全新安装；如需可各用一份全新快照）。
- **判定标准**：安装向导正常完成，无 UAC 异常中止被误报为成功；安装目录出现 `ag-relay.exe`、`node.exe` 与 `resources\gateway\`；开始菜单/桌面有启动项；安装后能启动应用。卸载同样能正常走完且不残留进程占用。
- **证据**：安装向导截图、安装目录清单、控制面板「已安装程序」条目截图、卸载后残留检查。

### ② 停留诊断日志页，新活动事件无需切页即出现

- **步骤**：启动已安装应用并让受管网关运行；打开诊断日志页并**停留在该页**；随后经面板显示的连接地址向受控假上游发起一个请求（必要时先制造 `gateway_started`）。
- **判定标准**：新写入的活动事件在**不切换页面、不手动刷新**的情况下自动出现（实时通知链路贯通「核心写入 → 壳服务 → Tauri → 面板」）；错误态与空列表能区分显示。
- **证据**：请求前后同一屏幕的诊断页截图（含时间戳）、`%APPDATA%\ag-relay\logs\relay-diagnostics.jsonl` 对应新增记录。

### ③ 修改连接设置重启后仍生效

- **步骤**：在设置页把本机端口与上游地址改为一个新的合法端口与受控假上游；保存后执行「安全重启并应用」。
- **判定标准**：重启后连接地址显示为新端口；网关在新端口监听（旧端口释放）；上游请求确实发往新上游；重启后设置从磁盘恢复、不丢失。
- **证据**：设置前后截图、重启后端点截图、新端口/旧端口连通性检查、`%APPDATA%\ag-relay\` 内连接设置文件副本。

### ④ 应用内更新到签名新版：保留设置与日志、不掐断在途请求、恢复更新前运行状态

- **步骤**：在被测（测试公钥）版本内检查更新，指向测试更新源上**版本号更高**的测试签名新版；对一个**受控慢上游**发起持续超过 10 秒的在途请求，然后确认更新。分别在“更新前网关运行中”和“更新前网关已停止”两种起始状态各做一次；涉及等待逻辑的改动再覆盖取消与预算到期。
- **判定标准**：
  - 检查阶段只显示版本与说明，**未确认不下载、不安装**；
  - 确认后先完整验签，再满足安全停机条件才安装；等待时暂停接收新请求、显示进度，已有长请求自然完成，不强制中断；新版等待可取消，最长 10 分钟；
  - 等待期间取消或预算到期时，**不安装、不退出**，恢复接单且原请求仍能完整完成；确认停机／安装阶段的取消边界按实际阶段说明，不能承诺安装开始后仍可撤销；
  - 安装完成重开后，连接设置与诊断日志**保留**；
  - 重开后按更新前状态恢复——**更新前运行**则恢复运行、**更新前停止**则保持停止（不被默认自启覆盖）。
- **证据**：检查/确认/排空/重开各阶段截图、在途请求完整完成的证据、更新前后设置与日志副本对比、两种起始状态的重开行为截图。

### ⑤ 无预装 Node 的干净机器可运行

- **步骤**：沿用第 ③/④ 步之前的「干净机器基线」（PATH 无 `node.exe`）；全新安装后启动应用，让受管网关起停、转发一次请求并写入诊断。
- **判定标准**：应用与网关在**无系统 Node** 的环境下正常运行；核心由随包 `node.exe` 拉起；诊断日志正常落位。
- **证据**：`where node` 空结果截图、启动与转发成功截图、诊断新增记录。

### ⑥ 被篡改的更新包因验签失败被拒

- **步骤**：在测试更新源上，把第 ④ 项的新版安装器（或对应 `.sig`）**改动一个字节**；在应用内检查并确认更新。
- **判定标准**：验签失败，**拒绝安装**；应用**不停机、不退出**、网关继续运行，并给出可理解的失败提示。
- **证据**：篡改方式说明（字节位置，不附真实密钥）、失败提示截图、更新尝试前后网关仍在运行的证据。

## 执行后记录

- 未执行的条目不得因宿主机只读验签或 mock 测试通过而记作通过。
