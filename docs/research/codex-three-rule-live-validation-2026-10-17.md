# 三条删除规则：真实通道隔离对照

日期：2026-10-17，北京时间 12:23:02–12:23:51。

> 历史实验：文中“当前”“目前”“现用”均指 2026-10-17 当次实验的通道与网关，不代表现行策略。普通函数续接仅为当次未完成验收，不表示现在不可做。

## 结论

**在当前通道的这组真实样本中，三条规则一起执行后，网页搜索历史的两次续接都成功，且都是一次上游尝试。** 对照组沿用现用网关的保护策略：一轮经历三次 Azure 跨资源错误后第四次成功，另一轮以跨资源相关 400 失败。

这支持群里报告的“去掉这类历史状态后更容易续接”的方向，也说明现有“只要历史里有网页搜索就始终保留全部推理和编号”的保护过于保守，不能作为最终恢复方案。但本次仍不能证明无损、长期稳定或原用户对话已恢复。

**没有应用实验规则，没有更改现用核心、真实 config 或原对话，没有打包发布。**

## 授权与隔离范围

- 用户明确选择真实通道对照，接受正常模型用量。
- 使用与截图相同的模型 `ccs-pc54109/gpt-6-astra`。
- 链路：临时请求脚本 → 当前本地 CC Switch → 当前 AG Relay → 真实上游。AG Relay 的对应诊断记录已核对。
- 输入只有合成任务、合成记忆标记和公开 Python 文档查询；不读取、复制或重放真实聊天，不运行模型生成的工具命令。
- 凭据只从现有配置中加载到内存，用于已配置的本地入口；不写入参数、输出或实验文件。
- 承诺上限 8 个客户端请求，实际 **6 个客户端请求、9 次 AG Relay 上游尝试**；没有新增客户端自动重试。每次超时 90 秒、总预算 8 分钟，实际约 49 秒结束。
- 两组统一使用 `reasoning.effort=low`、`max_output_tokens=1536`。这不是原长对话的完整参数重现。
- 对照组仍会经过现用网关原有的可选 ID 清理，因此不是完全无网关的原始请求。
- 相同的真实搜索结果作为四次续接的输入，按“对照 → 三规则 → 三规则 → 对照”顺序交叉发送。内部兼容缓存身份按请求隔离，外部会话标识保持一致。

## 被验证的规则

按截图的删除语义实现，不声称复现未知管理界面的具体路径解析引擎：

1. `input.#(type=="reasoning")#`：删除所有 reasoning 条目。
2. `input.#(id)#.id`：删除剩余输入项的顶层 id，不递归删除内部字段，不删除 call_id。
3. `previous_response_id`：删除顶层 previous_response_id。

## 真实搜索对照

先发起一次全新原生网页搜索，真实响应包含 **2 条 reasoning、1 条 completed 的 web_search_call（action=search）及回答正文**。随后只要求重复合成标记和此前文档链接，不允许再次搜索。

| 请求 | 额外执行三规则 | 实际结果 | AG Relay 上游尝试 | 客户端耗时 | 合成标记检查 |
| --- | --- | --- | --- | --- | --- |
| 搜索历史生成 | 否 | 完整成功 | 1 | 15.41 秒 | 不适用 |
| 对照 1 | 否 | 前 3 次跨资源错误，第 4 次成功 | 4 | 17.30 秒 | 通过 |
| 三规则 1 | 是 | 完整成功 | 1 | 5.81 秒 | 通过 |
| 三规则 2 | 是 | 完整成功 | 1 | 4.14 秒 | 通过 |
| 对照 2 | 否 | HTTP 400，客户端错误文本匹配 Azure 跨资源模式 | 1 | 1.82 秒 | 无成功回答 |

实验组请求中已无历史 reasoning、无输入项 id；**web_search_call 本身及 action/status 仍保留，只移除了其 id**。当前通道实际接受了这种输入，并返回新的 reasoning 和完整回答。因此不能把“删掉旧 reasoning”误解成“模型不再进行新的推理”。

输入侧校验确认，除了删除的 reasoning 和顶层 id，其余非 reasoning 项的载荷保持相同。合成标记被正确复述，只证明这个简单内容检查通过，不证明长任务质量或推理连续性完全不受影响。

> 重要：本轮输入本来就没有 previous_response_id，因此第三条在真实搜索对照中没有产生变化。观察到的改善不能归功于第三条，也不能据此推荐对任意请求无条件删除它。

## 普通函数工具：未完成真实续接验收

第 6 个请求要求模型调用唯一的合成函数 `fixture_lookup`，收到了 reasoning 和 function_call 输出项；但流里没有标准完成终止标记。AG Relay 同样记录 `sawTerminal=false`、`terminalKind=null`。

本轮没有把 HTTP 200 或“看到工具调用”当作完整成功；没有继续执行普通工具的两组续接，没有自动追加请求。**普通函数续接在本次实验中未验证通过。** 工具调用仅是合成数据，没有执行任何模型提出的本地操作。

## 离线结构检查

使用同一删除函数对四种合成结构做独立断言：

- 原对象不被改写；重复执行规则不会继续改变结果。
- 普通 function_call / function_call_output 的 call_id 配对保留，嵌套参数、输出中的 id 也保留。
- reasoning 及其密文被删除，属于有损历史处理。
- 原生网页搜索顶层 id 被删除。虽然当前通道实测接受，仍不代表其他严格按官方必填字段校验的服务会接受。
- item_reference 的 id 也会被删除，使引用失去载荷；全局无差别应用存在风险。
- 只有 previous_response_id 承载前文时，删除指针不会自动把服务端历史补成内联消息，可能直接丢失前文。

## 能证明与不能证明

**已证明：** 当前真实通道确实能接受本组“删历史推理 + 删全部输入项 id”的原生搜索续接；对照历史存在实际 Azure 资源不兼容，单纯保留并重试不稳定。

**未证明：** 用户原对话已恢复；该策略无损；长期、多轮或高推理强度时仍稳定；open_page / find_in_page 等其他原生搜索动作均可接受；普通工具的完整真实续接；有服务器端历史引用时删除 previous_response_id 的真实效果；三条规则中的每一条分别贡献多少效果。

本轮没有恢复旧对话，也没有修改目前的保护策略。后续若实现恢复，应明确区分当前特定通道的有损兼容与通用无损转发，不能因为一次通道接受缺少搜索 id 的请求就放宽所有客户端、所有上游的历史规则。
