## v0.3.21：不可见加密推理保持可重试

明确、无冲突识别的 Claude/Codex `POST /v1/responses` 在仅收到不可见的加密 reasoning 项时，暂存该轮事件。`output_item.added/done` 含非空密文且没有可见摘要、推理正文或未知内容块时，不触发交付；完整推理仍参与原有生成进展与去重。普通可见思考、正文、工具及既有搜索边界沿用。

- 取消、已有次数和时间预算、缓冲容量限制保持；可见思考、正文、客户端工具、完成搜索或未知载荷交付后仍不重放。

## v0.3.20：Claude / Codex 未覆盖错误的单次激进保底

用户选择以部分旧推理连续性换取更强兼容性，减少每遇到新文案就重新开发发布的成本。新保底不依赖具体历史关键词，也不把每个未知错误登记成新的专用修复规则。

- **范围**：只在明确、无冲突识别的Claude/Codex `POST /v1/responses`、`historyMode=on_error` 且本组 `uncoveredErrorFallback=true` 时参与。两组默认true，可单独关闭；ZCode、未知/冲突身份、其他端点和 `off/always` 保持原行为。
- **流程**：合格的未覆盖错误首次发生后原样确认一次；第二次仍属未覆盖错误时，只调用一次现有安全历史修复器。两次文案不必相同，但中间的已知错误、网络异常或空回应会重置确认。正常首发及独立的Codex编号预清理不因保底改变。
- **资格**：200必须有真实JSON错误信封或下发前SSE `stream_error`；400/409/422允许有效错误字段或非空纯文本；404/500必须结构化。HTML错误页、无有效字段、空流、读取超时、缓冲超限不算候选；401/402/403/408/413/429/502/503/504不启动保底。
- **明确排除**：同时检查code与type，并仅用去掉编号/URL干扰后的错误原因，排除鉴权、余额/额度、内容限制、模型/上下文/请求大小、真实限流、超时/网络/普通拥堵及部署缺失。通用包装码、单个 `unavailable`、泛化 `not supported` 或item/resource不存在不能单独构成否决。旧全局分类不变，避免新保底改变其他客户端行为。
- **剥离与保留**：复用 `repairResponsesItems` 去旧reasoning和适用item id，要求完整工具配对。Codex按既有规则配套去搜索编号并保留action/status/扩展；Claude不新增未知历史类型处理。正文、工具参数/结果、`call_id`、身份、模型、元数据和 `prompt_cache_key` 保留，不修改本地聊天。
- **拒绝条件**：服务端引用、未知/压缩项、非推理密文、不完整工具历史或没有可安全删除的内容，直接返回当前错误。专用修复/绑定恢复的拒绝或停止、已做过的有损处理、会话预清理和其他改体路径不能被新保底绕过。
- **真实两次上限**：候选只在本请求内使用，发送前固定至多两次、且不超过剩余原次数；紧贴fetch扣减，网络失败及混合429/503也计数。候选冻结，不再进入status/account/shape修复，不登记兼容记忆。最后一次失败不再退避等待，也不能靠部署/网络扩次绕过上限。
- **收尾**：HTTP/JSON保留末次状态/错误载荷；下发前SSE以502错误信封保留末次code/type/message，不把陌生错误伪装成429。网络/预算耗尽仍用既有封装。取消立即生效，已交付内容或工具后不重放，不截断健康长流。
- **观察与配置**：沿用 `item_error` / `repair_applied` / `repair_refused`，增加 `kind=uncovered_error_fallback`；不新增事件或独立看板。旧磁盘配置只在内存补默认值，显式false保留；旧核心缺新字段时active策略保持未核实，不能假装已启用。

验证基线为已发布v0.3.19 / `a9d5b6b`的核心及同版本依赖。新主路径先红后绿；Node组合运行493项，492通过、1项旧绑定用例超时取消（无断言失败），该用例随后单独通过，整组37项绑定回归亦通过，未放宽断言或超时。Rust诊断25项、策略设置14项、策略回执5项及新开关生效1项通过；前端配置/组件9项、类型检查及全假IPC浏览器交互通过。验证包含默认新路径、关闭保底的旧版差分、末次错误保留、候选真实发送上限、取消和工具/身份/缓存键保护。

不以假上游通过冒充真实上游的恢复率或无损质量保证；没有安装、重启或修改现用网关。

## 2026-11-01：删除自动换键并收拢恢复编排（源码已改，未发布）

用户明确要求删除缓存键切换策略，不是提高触发阈值或增加开关。此前少量“换键后恢复”的实验不足以证明连续两次限流就应干预，自动改键还可能损失缓存复用；本次不承诺删除后真实恢复率、费用或速度必然改善。

- **彻底删除运行时换键**：不生成替代键、不改写/删除客户端的 `prompt_cache_key`、不登记成功替代键，不保留换键的专用计数、作用域与过期维护。无键请求不注入缓存键；历史兼容记忆独立保留。没有触发既有历史处理的请求按原字节转发。
- **保留已有修复**：账号绑定旧推理不可用、Codex 会话绑定只去编号、历史兼容及工具配对规则不变。限流不触发新的历史改写，取消、次数/预算、空占位/搜索和已交付不重放规则不变。
- **集中恢复安排**：HTTP错误、200 JSON错误、下发前SSE错误复用 `recoverFailure` 编排；继续复用已有分类、状态修复和历史修复。未知HTTP透传、未知SSE兜底重试、未知JSON后续处理，以及各载体错误状态/载荷的差异保留。等待仍处于原尝试的控制器清理周期内，不提前增加发送计数。
- **只读观察保留**：新核心仅写 `request_summary`，以实际尝试/错误总数替代换键前后分段；保留有限限流子类、等待提示、首内容/总耗时、真实终态及既有用量。无键哈希、候选或映射字段，不额外解析SSE、采集正文或调用上游。上游等待提示仍不改变实际等待；缺失用量不补零，返回JSON不冒充模型完成。
- **历史日志仍可读**：面板保留旧 `cache_route_summary` 的解释，不再由核心写出；当前24项事件与历史读取兼容清单分别验证，不用死代码维持旧枚举。

## 2026-11-01：Claude 与 Codex 持续限流后的缓存路由恢复（历史，已撤销）

现场同一 Claude 请求在本地分别尝试 57、54 次后被客户端约六分钟超时取消，客户端又按相同请求摘要重新发送。上游实际返回 `rate_limit_exceeded`，正文为模型所在区域的 token rate limit；仅用新 TCP 连接不解除与 `prompt_cache_key` 相关的持续拒绝。

真实受控对照中，同一份旧历史与工具载荷在旧缓存键下重复限流；只更换缓存键后 42.7 秒完整成功。省略缓存键的另一笔请求也成功。这支持“缓存亲和性相关的持续限流”，不声称已观察到上游内部调度实现。原始 Messages 的 152 条消息逐条哈希核对；Responses 请求按转换规则重建，不冒充原生抓包的字节级重放。

- 仅无冲突识别的 Claude 或 Codex `POST /v1/responses`，且请求已提供非空字符串 `prompt_cache_key`。ZCode、未知／冲突客户端、其他端点及无缓存键请求不变。
- 连续两次明确 `rate_limit_exceeded` 后，在剩余次数和时间预算允许时，当次请求最多更换一次缓存键。鉴权、额度、历史错误和普通网络故障不触发；不修改原生会话头、模型、输入、推理、搜索、工具、服务端引用或其他请求字段。Codex 的已登记会话预清理仍先执行，换键不绕过它。
- 成功的新键按上游、凭据、模型及原缓存键隔离记忆，后续请求复用；失败候选不登记。内存记录沿用既有容量／存活时间上限，只保存作用域哈希和随机生成的键。新键第一次可能需要重建缓存，不能承诺没有额外缓存成本。
- 不增加重试次数或时间预算，不改客户端自动重试配置。取消立即结束等待，已交付内容不重放。没有新增有损历史处理；既有明确跨资源错误触发的 Claude 历史兼容策略仍然保留。
- 2026-11-01 补最小诊断（源码已改，未发布，也未部署到现用网关）：每个进入业务处理的 `POST /v1/responses` 请求结束时写一条 `cache_route_summary`，记录输入字节/条目数、起始与首末实际键的脱敏摘要、换键前后尝试与限流次数、真实终态、首次内容/总耗时及现有终态用量；正常首发成功也记录作同期对照。限流子类与上游等待提示只观察，不用于等待或换键判断。事件码由 23 增至 24。该记录不改变重试、预算、取消、身份、历史或缓存键选择。

隔离真实核心验证：旧核心的缓存路由复现返回 429，新核心第三次发送恢复且下次首发复用成功键。定向覆盖 HTTP／JSON／SSE、作用域隔离、一次轮换、失败不记忆、取消和交付边界，并对照既有 Claude 历史行为、Codex 会话绑定与预清理用例。

同一现象在 Codex 通道早已出现：2026-10-28（v0.3.14／0.3.15 上线前）的日志已有 38 笔请求超过 10 次重试；10-28～10-29 两轮日志中 Codex 分别有 191 笔超过 10 次、31 笔超过 50 次，最高 93 次才成功、110 次耗尽。两版更新只收紧 Codex 流式交付时机（搜索缓冲、空占位），没有改动重试次数、退避、预算或缓存键处理，因此不能归因于 0.3.16／0.3.17 的回归；更符合上游对该缓存键持续限流、旧网关只做同请求重试的现有判断。

真实旧历史经修改后独立核心共发出 4 次上游请求，46.4 秒收到 `response.completed`：第一次明确跨资源错误按原有策略去掉 84 条旧推理，随后两次限流，换缓存键后的第四次成功。原对话文件未改，返回工具未执行；这证明重建旧请求的恢复，不代表已升级现用程序。未安装、重启、发布或改变生产配置。

## 2026-11-01：账号绑定的旧推理不可用

现场（Claude 经中转，非流 Responses，19:33）在上游请求 400 后连续重试 6 次、42 秒被客户端取消；截图文案为“the upstream account bound to this conversation is unavailable; start a new conversation without previous encrypted reasoning items”。该报错**不属于 Astra 或 Claude 专属**：按用户更正，Codex 也可能出现；规则不按客户端或模型写死。

- 仅 `POST /v1/responses`，且在 HTTP 400/409、200 JSON 错误或下发前 SSE 错误中**同时**出现两条短语时才进入。单独 `unavailable`（普通 503）、`rate_limit_exceeded`（普通 429）不触发，不改写请求体。
- 首次命中后删除旧 `reasoning` 项：保留 message、function_call/output 及 `call_id`、工具参数/结果、`client_metadata`、UA/鉴权等身份头；Codex 按既有规则另去可选 item id，Claude 保留。
- 连续报同一账号错误时，**原始发送一次 + 最多两次修复后发送**，仍报同错则停止。计数只在该账号错误分支递增；中途转为普通429/503时仍沿用既有普通预算，不将所有修复后发送合并为新的两次上限。不登记“下一条请求自动删推理”的兼容缓存。
- 不扩大既有会话绑定/跨资源修复；为这两次修复重试保留发送机会，但仍受总时间预算、取消与已交付不重放约束。

## 2026-10-17：Codex 与通用客户端的独立策略设置

设置现在可以分别控制 Codex 和通用客户端的重试与兼容行为，避免为了一个客户端调整参数却影响另一个。以下是提供新配置时的边界；**完全不设置 `PROXY_POLICY_JSON` 时，既有环境变量及原处理行为保持兼容**，不是将所有独立运行的核心强制改为桌面默认值。

### 配置与生效回执

`PROXY_POLICY_JSON` 使用 `{schemaVersion: 1, profiles: {codex: Profile, general: Profile}}`；两组 `Profile` 都采用以下扁平字段，不在各组中另套一层 `retry` 或 `history`。仅 Responses 请求选择这两组：严格识别的 Codex 使用 `codex`，其余使用 `general`；其他接口仍保留既有运行参数与行为。关闭历史模式不会抹掉客户端身份，也不会让 Codex 落入通用空响应修复。

| 字段 | 含义及桌面默认值 |
| --- | --- |
| `maxAttempts` | 常规尝试预算，含首次发送；两组默认 `110`，不是无例外的全局硬上限。部署/连接异常及空回应仍可提高到至少 8 次，定向修复也可能追加少量尝试 |
| `baseDelayMs` / `maxDelayMs` | 基础重试间隔与间隔上限；两组默认 `500` / `1000` 毫秒 |
| `totalBudgetMs` | 重试总时间预算；两组默认 `500000` 毫秒，不用它截断已经正常交付的长流 |
| `connectTimeoutMs` | 单次尝试等待上游响应头的上限；两组默认 `220000` 毫秒，请求体每多 1 MB 核心再追加 `30000` 毫秒（受总预算封顶）。上游拥堵时通常需要 150–230 秒才回首个字节，调低会让本来能到的请求被提前中止 |
| `historyMode` | `off` 关闭历史降级，`on_error` 在明确错误后处理，`always` 首发前尝试整组处理；默认 `on_error` |
| `historyConfirmations` | 当前请求内、同类明确历史错误的累计确认次数；默认 `1`，Codex 可设 `1..4`，不能超过发送次数上限 |
| `uncoveredErrorFallback` | 未覆盖错误的单次历史降级保底；两组默认 `true`，仅严格Claude/Codex且 `on_error` 参与，确认一次后候选最多实际发送两次，不跨请求记忆 |
| `stripItemIds` | 独立的 Codex 首发可选编号清理；Codex 默认 `true`，general 必须为 `false` |
| `rememberSession` | 是否允许读取、登记兼容会话记忆；两组默认 `true`，仅 `on_error` 模式参与，`off` / `always` 不读写记忆 |
| `repairStatus` | 仅在精确拒绝 `input[n].status` 时尝试字段修复；两组默认 `true` |
| `retryHistory` | 不能安全改写时是否允许保留历史有限重试；Codex 默认 `true`，general 必须为 `false` |
| `emptyResponseRepair` | 通用空响应一级形状修复；general 默认 `true`，Codex 必须为 `false` |
| `emptyResponseDropReasoning` | 一级确实改动后仍失败，是否允许二级删除推理；general 默认 `true`，Codex 必须为 `false` |
| `emptyResponseNormalizeAfter` / `emptyResponseReasoningAfter` | 空响应两级触发门槛；默认 `2` / `6`，二级门槛须大于一级，且不能只开二级而关闭一级 |

核心在启动时校验并规范化设置，运行中使用该次启动的固定快照。`/_relay/status` 顶层返回 `policy: {revision, settings}`：`settings` 是完整生效配置，`revision` 是该规范化快照的 SHA-256 修订号，用来识别配置是否一致；不能只因桌面表单已经改变就声称运行实例已采用新配置。类型错误、显式 `null`、未知字段、非法范围、不支持的模块组合及不可解析 JSON 均在启动监听前拒绝，不悄悄忽略或纠正。

### 开关独立与历史安全边界

- `historyMode=off` 禁止历史降级和会话记忆读写，但不覆盖独立的 `stripItemIds`、`repairStatus` 或通用空响应修复开关。关闭某一修复不重新定义原有错误信封、通用重试或耗尽状态码。
- `on_error` 按**当前请求内、同类错误累计**，不是旧版要求相邻错误的策略。跨资源与失效推理等不同类别分别计数；限流、5xx、网络错误不计入，也不清除此前同类证据。在未使用已许可的会话记忆时，到门槛前不做整组有损降级；独立开启的首发编号清理仍可按自身规则执行。
- `always` 的提前降级先校验整个历史，再一次性采用处理结果。Codex 完整内联搜索可连同旧推理和资源编号成组处理，保留搜索 action/status、来源扩展、普通与自定义工具参数和结果、`call_id` 及嵌套内容；general 不套用 Codex 搜索专用变体。两者的提前模式都要求工具调用与结果一一完整配对。
- 非空 `previous_response_id`、`conversation`、`item_reference`、压缩密文、未知项、未知搜索动作、非推理密文、不完整或重复工具结果不能被盲删。**提前整组校验失败时整个原始 body 逐字节保留，包括 `message.id` 和空白**；跳过该请求的编号及缓存预清理。后续空响应与明确历史错误也不能经较弱的处理路径再次局部修改这份已拒绝的历史。此加强仅适用于新提前模式，不改写 general 默认报错后的既有规则。
- 通用空响应一级处理可省略编号与消息类型，二级才可能删除旧推理。门槛可调整；一级实际没有改变请求时，不能空转升级到二级。历史模式关闭不禁止独立启用的空响应修复。
- 历史模块仍限于既有 Responses 请求范围。取消、已交付内容后不重放及第五次历史错误停止等边界继续有效。三次发送上限按 [2026-10-22 的作用域修正](#retry-cap-scope)，只约束本次明确历史错误后的真实有损降级，不约束预清理／提前处理。有损降级仍可能损失推理连续性和搜索的资源关联，不能等同于恢复完整历史。

### 隔离验证

## 2026-10-22：统一错误证据与分类，排除编号干扰

真实 HTTP 400 加密推理错误附带的请求编号含 `502`，旧临时错误正则把编号中的数字当成服务器故障，跳过历史修复后又按 400 直接透传。该问题属于分类证据范围与入口优先级冲突，不是只有 `502` 一个例外。

- HTTP 错误、下发前 SSE 错误和 200 JSON 错误共用 `classifyError`。只从已有明确错误信封读取经过字符串类型校验的 `code/type/message`，不扫描外层调试字段、成功输出或请求正文。可解析 JSON 没有错误信封时不回退全文猜测；HTTP 非 JSON 错误保留纯文本兜底。
- 分类用的原因视图排除 request/trace/response/item 编号、已知条目句柄与 URL。原始错误仍用于返回，不修改用户或工具数据。保留 `ws_/rs_` 类型骨架和 `input[n].status` 下标，避免为了排除编号而破坏精确修复识别。
- 具体错误码按明确集合精确匹配，英文文案限定词边界和有意义的短语。编号中的 `401/402/403/408/429/502/503/504` 不参与判断；文案中的状态数字只接受明确 HTTP/status/error 表达，不再因裸 `gateway` 或 `balance` 推断服务器或余额故障。
- 明确鉴权、余额、上下文、模型和审核失败优先于部署或历史文案；真实 HTTP 401/402/403 不进入字段或历史修复。具体暂时错误码即使包在 HTTP 400 中，也原体有限重试，与 200 JSON/SSE 的原因判定一致。HTTP 永久错误仍保留原状态及原信封，200 内嵌永久错误按既有 400/402 格式返回，因此统一分类不等于强行统一传输状态。
- 泛化 `invalid_request_error` 类型本身不证明永久失败。未知 HTTP 400 仍原样返回；未知下发前 SSE 仍有限重试；未知 200 JSON 不新增重试。只有明确历史错误才能进入既有安全有损修复，缺配套搜索推理仍限严格 Codex。未设置策略信封的独立运行核心也采用同一分类安全规则，但默认配置、正常历史修复能力不变。
- 不增加默认次数、退避或预算，不放宽历史类型、工具配对、缓存隔离、一次修复、取消和已下发不重放限制；不改动 `1d8b522` 已提交的可取消安全退出控制。

隔离回归通过真实核心子进程与假上游公共 HTTP 接缝验证。测试包含截图完整报错、短版首句、编号/URL/英文子串、无关 JSON 字段、非字符串错误字段、错误码与状态的冲突、三载体与旧配置、成功 JSON/SSE/纯文本原字节保留。新增分类测试均不请求真实上游、使用临时目录与随机非 8787 端口，清理仅限所持子进程。

本次不安装、重启或发布现用网关；仓库修复不会自动改变正在运行的版本。

最终验证：新增 **44 项 Node 分类回归**与 **2 项 Rust 集成契约**。使用 `1d8b522` 已提交核心作为临时差分基线，Node 历史、策略、安全排空三套合计 **196 项通过、0 失败、0 跳过**；Claude 正常转发、跨资源、失效推理及两级空响应五种差分保持一致。Rust `gateway_connection` **43 项通过、0 失败、1 项手动性能观察忽略**，诊断字典 **17 项通过**。最终诊断调整后再跑两项 Rust 分类契约和字典全部通过。核心语法、补丁格式检查通过；控制接口、可取消安全退出及启动部分与 `1d8b522` 逐字保持不变。没有真实模型请求、成品安装或发布验收。

## 2026-10-22：三次发送上限只约束真正的历史降级，中文无可用渠道按通道抖动

现用网关诊断显示：一天内 83 个 Codex 请求收到「修复版三次发送耗尽」的 503，全部发生在**会话记忆预清理**的请求上，其中真正的历史错误为 0，全是 200 流内 `rate_limit_exceeded`。同一时段 Claude 的 69 个限流请求有 67 个在 3 次左右的重试后成功。配置的常规 110 次／300 秒因此形同虚设。

原因是把「请求体被改写」当作「历史错误证据」：一旦会话被登记，后续每个请求首发前都会剥 reasoning，于是全部顶着三次上限。本次把两者分开。

- 新增本次请求内的 `historyRepairApplied` 标记，只在 Upstream 明确报出历史错误、且确实做了有损降级时置位。`postRepairSends` 计数、次数上限判断，以及“已达上限就不再退避”的快速收手，都改为检查该标记。
- **会话记忆的预清理（含首发剥 id、登记后的首发剥离）不再计入三次上限**；这类请求按本组常规次数与总预算重试。没有历史错误证据时不得按资源上限收手。
- 真正的历史降级行为不变：仍然一次修复、修复后冻结请求体、最多再发三次、历史错误累计五次。`always` 提前模式的整组改写同样不置位 `historyRepairApplied`——它没有上游错误证据，因此也不再被三次上限截断。
- 中文站点的「无可用渠道 / 无可用模型」并入 `DEPLOYMENT_TEXT`，按通道抖动处理：放宽到 `deployMaxAttempts`（默认 8）、间隔 `deployDelayMs`（默认 800ms），耗尽后返回可重试状态，不改写历史。此前只认英文 `no deployment`，中文文案落进通用 503 重试，实测把 Codex 后台辅助请求拖满 110 次、约 200 秒；这段时间会一直占着上游连接与限流配额。
- 未增加默认次数、退避或预算，未放宽历史类型、工具配对、缓存隔离、取消和已下发不重放限制。

隔离验证：`scripts/gateway-history.test.mjs` 新增「会话记忆预清理不占用三次发送上限」——登记会话后再次请求连续 4 次限流，要求实际发送 5 次并最终成功，且不得出现 `codex_resource_exhausted`；`scripts/gateway-policy.test.mjs` 新增「中文无可用渠道按通道抖动快速换道并收手」——要求 8 次内收手、5 秒内返回、且不改写历史。两项均以改动前核心为差分校准：旧核心下前者直接返回 503、后者重试至通用上限，测试失败。两套 JS 回归合计 **188 项、183 通过、0 失败、5 跳过**（跳过项为需真实通道的 Claude 差分）。

本次不安装、重启或发布现用网关；仓库修复不会自动改变正在运行的版本。
