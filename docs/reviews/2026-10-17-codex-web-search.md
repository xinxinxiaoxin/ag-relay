## 为什么会报错

截图的意思是：历史中的一条网页搜索记录 `web_search_call` 依赖某条 `reasoning` 推理记录，但服务端找不到配套项。

已在真实核心中复现三处缺口：

1. 首发清理保留搜索编号，却删除推理编号。
2. 错误后恢复以及已登记会话的首发预清理，删除整个推理项，却保留搜索项。
3. 截图这种“缺必需推理”的错误不在现有恢复识别范围。

本机实际加载的是 v0.3.8，不是更新未生效。脱敏诊断中也有移除 19 条推理后失败的请求，但没有保存报错正文或条目编号，不能把截图唯一对应到某条请求。

Claude 当前使用正常不代表相同剥离对所有历史都安全。客户端名称不能决定协议；本次差异是 Codex 请求包含不能与推理拆开的内置搜索历史。可以共用“记住兼容处理”的策略，但不能不检查依赖就共用“删推理”的动作。

## 本次修复

- 含网页搜索的 Codex 历史保留全部推理及其编号，不猜哪一条是配套项。
- 错误后恢复和会话预清理均拒绝拆开搜索与推理；不删搜索、不转成普通文本、不补造推理。
- 无法安全改写时沿用有次数和时间边界的保留历史重试，不假报修复成功或新增清理会话。
- 精确识别截图错误，仅作用于严格识别的 Codex Responses 请求；鉴权、额度、限流、上下文超限等仍按原规则处理。
- 无搜索请求、其他客户端、取消和已下发内容后不重放的既有边界保留。

**能力边界：这能防止网关继续破坏历史，不是上游跨 Azure 资源问题的根治。** 若客户端发来时就缺了配套推理，本地不能还原其密文；保留历史重试也不保证另一通道一定接受。

## 热修后的真实使用反馈（11:56）

用户在同一旧会话继续请求后仍失败。只读诊断核对确认：新核心 `305cecc7…` 仍在运行；11:56:15–11:56:47 的 Codex 请求进入网关时为 77 项、19 条 reasoning，五次尝试仍为 77 项、19 条 reasoning。首发移除 56 个其他可选编号，但 `removedReasoning=0`、`repairCount=0`；五次错误均为 `azure_resource_mismatch`，最终达到既有五次边界。

这份真实反馈说明：**停止破坏性剥离已生效，但旧会话在当前上游仍无法接续。** 不能把隔离回归通过说成该用户会话已恢复成功。原始推理数量相同也不足以单独证明指定 `rs_…` 编号及密文都正确；网关不会据此伪造或继续删除依赖项。网关仅改写内存中的发送副本，不修改 Codex 本地对话文件。

进一步只读核对本地会话：截图指定的 reasoning 仍作为结构化 `response_item` 存在，编号保留、密文非空；相应 `web_search_call` 也在，搜索状态为 completed。该文件没有历史压缩事件，所查各轮模型未变化。因此不能说本地原会话已被剥坏或永久丢失；但本地落盘完整不等于当前上游能访问它。继续原会话需要发送链路与上游支持接续这份旧历史；为了尽快继续工作，可保留旧会话另开干净会话，仅迁移任务摘要和必要项目文件，不携带旧的原始工具条目。

## 群里 Azure 配置是否有效

使用本机实际程序 **Codex `0.163.0-alpha.10.2`**，而非拿最新版文档代替本机行为。临时 `CODEX_HOME`、空工作目录、假凭据和动态假上游；不访问现用网关、真实模型或真实会话。

只改变提供商标识与名称，其余一致（包括 `requires_openai_auth=true`），每组捕获首发和带人工历史的下一次请求：

| 配置 | `custom / custom` | `azure / Azure OpenAI` | `azure / Azure` |
| --- | --- | --- | --- |
| 实际请求数 | 2 | 2 | 2 |
| 路径 | `/v1/responses` | 相同 | 相同 |
| `store` | `false` | 相同 | 相同 |
| 历史推理编号、密文 | 保留 | 保留 | 保留 |
| `previous_response_id` | 无 | 无 | 无 |
| Bearer 假凭据／`api-key` 头 | 有／无 | 相同 | 相同 |
| 捕获的请求结构 | 基准 | 与基准相同 | 与基准相同 |

结论：**普通请求上，没有观察到仅改这些标签就能解决跨资源历史错误的效果，所以没有改真实 config。**

源码还有一个不能忽略的区别：本地代理地址下 `name="Azure"` 才触发该版本的 Azure 识别，`name="Azure OpenAI"` 不触发；Azure 识别会改变远端历史压缩能力的默认值。本次没有触发压缩，因此不声称已实测该路径，也不能笼统说改名完全没有任何作用。

`disable_response_storage` 不在该版本公开配置 schema 中，普通请求构造本来就固定 `store=false`，不能把这个结果归功于截图中的该字段。重试次数设为 100 不是历史修复；本次没有把它写入真实配置。`requires_openai_auth` 涉及凭据来源，不能只因上游使用 Azure 就随意改变。

“改配置后重开对话成功”同时改变了两件事：配置和旧历史。新会话不携带原问题历史，可能本来就成功；它不能单独证明配置有效。客户端标签也不能证明中转把后续请求固定到了同一个 Azure 资源。
