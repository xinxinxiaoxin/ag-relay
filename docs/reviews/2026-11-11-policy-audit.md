# 网关策略审计

2026-11-11；代码基点：v0.3.22 / `ad64eb60259150a8d39e529d4052bdada1999eb4`。

## 结论

保留现有策略模块和恢复机会，精简内部重复判断。修复账号恢复在常规次数末尾可能没有完成响应，以及非流式正文中途断线后跳过剩余重试的问题。部署最低次数与账号错误优先级沿用 v0.3.22 的实际行为。

本次修复两项行为问题，完成三处局部整理。HTTP、200 JSON、下发前 SSE 继续共用恢复入口；历史改写继续共用同一修复器。v0.3.22 的代理消息支持符合现行边界。

## Spec：行为与约定

### 1. 账号恢复在常规次数末尾必须完成响应

影响 Claude、Codex 的 Responses 请求。常规次数为 3 时，上游依次返回“账号绑定旧推理不可用 → 限流 → 相同账号错误”，第二次账号恢复未取得下一次发送机会，循环结束后响应仍未关闭，客户端只能等到超时。

每次获准的账号恢复现在都保证下一次实际发送。上述场景第四次发送成功，继续沿用同一份已删旧推理的请求。账号恢复仍最多两次，受总时间预算与取消约束，不登记会话兼容记忆。

约定：[账号绑定推理](../retry-boundaries.md#account-reasoning-unavailable)。验证涵盖 Claude/Codex × HTTP/JSON/SSE 六种组合。

### 2. 部署最低次数保留常规重试机会

该类别按错误原因匹配 `no deployment`、`deployment to match`、无可用渠道、无可用模型、无可用线路或模型不存在。它不是某个固定服务商的名字，进入该分支仍可能通过后续请求恢复。

`deployMaxAttempts=8` 是较小常规预算的最低尝试机会；配置 110 次时仍保留 110 次，同时服从原有时间预算及已适用的历史恢复上限。连续 8 次部署错误后，第 9 次成功的请求应由网关继续处理，不提前返回客户端。

约定：[重试机会与账号恢复](../retry-boundaries.md#policy-budget-priority)。验证覆盖 Claude/Codex × HTTP/JSON/SSE，使用 `maxAttempts=110`、`deployMaxAttempts=8`，要求第 9 次成功且请求体不变。

### 3. 明确账号绑定错误沿用专用恢复

HTTP 200/400/409 同时包含“upstream account bound to this conversation”和“without previous encrypted reasoning items”时，继续使用既有的去旧推理恢复。错误包装码不能单独证明该请求无法恢复。

测试覆盖 `invalid_api_key`、`insufficient_quota`、`rate_limit_exceeded`、`server_error` 与完整双短语并存的场景：假上游在旧推理被移除后接受请求，要求第二次发送成功。没有双短语的普通鉴权、额度、限流等错误仍按原分类处理；真实 HTTP 401/402/403 不进入账号恢复。

约定：[账号绑定推理](../retry-boundaries.md#account-reasoning-unavailable)。这些场景证明应保留恢复机会，不用于推断真实服务商每个错误码的含义。

### 4. 非流式正文断线保留剩余恢复机会

上游返回 200 或 503 后，正文只传到一半就断线时，原实现的读取异常绕过本次尝试，直接由最外层返回 502。配置五次时实际只发送一次，却在错误正文声称已经发送五次。完整返回的临时错误则能正常进入下一次尝试。

HTTP 错误正文和非流式成功正文现在集中到同一处完整读取，读取失败由当前尝试的网络恢复处理。重发沿用当前请求字节与身份，实际次数由已有发送计数提供。取消、总预算、部署最低机会、两次保底与三次有损降级上限继续生效；真实 401/402/403 不新增本地重试，完整错误与 SSE 的既有处理保留。

约定：[非流式正文恢复](../retry-boundaries.md#response-body-recovery)。新增 18 项隔离回归覆盖 Claude/Codex、200/503 半截断线后第二次成功、第九次成功、实际次数、预算耗尽、慢正文、取消和恢复计数。

## Standards：实现结构

- 删除保底准入中的四个冗余条件及绑定修复中的一个冗余条件。这些状态成立时 `repairedItems` 必然已经为真；它们在其他分支仍承担各自职责。已有绑定、账号、历史、状态修复后不能追加保底的用例继续约束行为。
- 空回应两级处理合成一次修复器调用，按阶段传入 `dropReasoning`。保留“一级确实改过”的独立状态，确保一级失败或无可改内容时不能升级删推理。
- 空回应注释改为现行触发规则与可配置门槛；部署说明与实际最低尝试次数规则一致。

这三项属于局部维护改进，不构成删策略或重建配置体系的理由。

## 历史修复 Interface 与测试启动工具

`repairResponsesItems(body, purpose, codexHistory)` 按既有用途选择处理规则。七处调用只传提前处理、会话兼容或已有错误类别，不再分别组合删除编号、删除推理、消息类型和工具完整性选项。

规则集中在同一个函数内部：提前处理要求完整工具配对；通用组会话预清理保留原有校验；会话绑定只去编号；账号与失效推理恢复按原客户端范围处理编号；空回应仍分两级；未覆盖错误保底要求完整工具历史。处理器返回的请求体、删除数量与拒绝原因不变。

三套网关测试共用 `scripts/helpers/gateway-fixture.mjs`，集中管理临时目录、随机端口、隔离环境、核心启动、IPC 就绪、实例身份核实和子进程清理。各套测试保留自己的假上游行为、请求样本、参数及断言；无效配置仍在 HTTP 探测前结束。共享工具可接收不同核心路径，供旧／新核心对照使用。

`scripts/gateway-history-parity.test.mjs` 从公共 HTTP 请求观察九类场景，分别验证 Claude 和 Codex。对照修改前核心的实际发送次数、完整请求字节、身份、返回结果及修复诊断；每个场景还独立要求预期发送次数与成功结果，避免两边同时失败却被算作兼容。

## 策略取舍

| 策略 | 决定 | 原因 |
| --- | --- | --- |
| 常规限流、服务拥堵重试 | 保留 | 原请求重发，承担暂时故障恢复 |
| 明确部署/渠道缺失 | 保留现行预算 | 后续通道可能恢复，最低 8 次不压低常规 110 次 |
| Codex 首发可选编号清理 | 保留 | 只处理可选编号，保留推理及搜索引用关系 |
| 定向状态字段修复 | 保留 | 只删除上游点名的一个字段，比整组改写更小 |
| 明确历史错误后的降级 | 保留 | 有错误证据后才移除旧推理，与首发清理不同 |
| 会话兼容记忆 | 保留 | 已有历史错误证据可供后续请求预清理；不能占用本次错误后的三次上限 |
| Codex 会话绑定去编号 | 保留 | 保留旧推理，不可与删除旧推理的恢复合并 |
| 账号绑定旧推理恢复 | 保留 | 上游明确要求去旧推理，两次机会与普通错误预算不同 |
| 未覆盖错误保底 | 保留 | 连续两次未知错误后有限尝试，减少对每种新文案增加专门策略的需要 |
| 通用组空回应分级处理 | 保留 | 空回应没有明确错误信封，需要独立计数与升级条件 |
| 空占位、内部推理、未完成搜索缓冲 | 保留 | 控制首次交付时机；交付后不重放，不能并入历史清理 |

不合并以下边界：首发编号清理与完整历史修复、两类客户端的兼容记忆、三次有损降级上限与两次保底上限。Node 启动校验、Rust 持久设置校验和前端即时校验分别服务不同入口，重复规则有必要保留。

## 已知限制

结论来自隔离验证，未衡量真实上游恢复率或长时间并发性能。源码与 Windows 安装包已随 v0.3.23 发布；本机已安装应用由用户自行更新。
